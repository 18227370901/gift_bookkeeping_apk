1项目全局概览

1.1 业务定位

本项目是「人情记账宝」产品矩阵的 Android 端交付形态，定位为安卓手机/平板上的礼金收付记账工具。产品矩阵共三个仓库：

  • Web 原生部署版（gift-bookkeeping-app）— 全功能版，含 Webhook、WebDAV 备份、专属宴席、AI 助手等
  • Docker Compose 版（gift-bookkeeping-app-docker）— 容器化部署版
  • Android APK 版（gift_bookkeeping_apk）— 本仓库，功能子集，聚焦礼金记录 CRUD + 用户权限 + 导入导出
核心架构真相揭露 README 第 14 行声称"用户可以在 Android 手机/平板上脱机离线使用"，但 main.py:4 硬编码远程 URL TARGET_URL = "https://ljp.loveyy.indevs.in:15001/"。APK 实际上是一个 加载远程 Web 页面的 Android WebView 容器，所有业务逻辑运行在远端 Flask 服务器上，设备端无任何本地后端服务或独立数据库。此为项目最重大的文档-实现漂移。

5.4 明确结论

【不建议替换框架，仅局部治理】

理由：

  1. 框架不是瓶颈 — APK 不打包 Flask，服务端 Flask 在当前用户量级下性能充分，更换框架（FastAPI/Django/Tornado）不能解决任何已识别问题。
  2. 核心问题是代码组织与安全漏洞 — 胖 Controller、权限双轨制、密码校验遗漏、死文件等问题与框架选择无关，可通过局部重构修复。
  3. 离线化改造是唯一值得考虑的架构级演进 — 但这也不是"换框架"，而是"变更部署模式"（远程 → 本地），且代价极高（需将 Flask+SQLite 打包进 Android），建议作为条件性演进保留，取决于用户是否真实需要离线能力。

7.4 兼容性迁移策略

init_database()（app.py:488-563）实现了手动增量迁移：

  1. db.create_all() — 创建所有表（已存在则跳过）
  2. 逐个 ALTER TABLE ... ADD COLUMN 添加后续版本新增的字段：
    • registration_tokens 表：max_uses, use_count
    • users 表：session_token, is_active, can_view_others, can_edit_others, can_delete_others
    每个 ALTER 语句包裹在 try-except 中（列已存在时 SQLite 报错被静默吞掉）
  3. 清空所有内存风控字典
  4. 检查并创建/同步管理员账号
迁移策略缺陷
  • 无版本号管理：无法判断当前数据库上次迁移到哪个版本
  • 静默吞错：except Exception: pass 掩盖了真正的数据库故障
  • 每次启动都执行全部 ALTER：即使列已存在也会尝试并报错（被 try-except 静默）
  • 无法回滚：无 downcast / downgrade 脚本

离线化改造风险评估
  • Buildozer + Flask 兼容性：Flask 依赖 WSGI 服务器，Buildozer 通常不打包 Gunicorn。需使用 Flask 内置 app.run()（单线程，不适用生产但个人使用可接受）
  • Android 后台服务生命周期：Android 可能在内存不足时杀掉后台 Python 进程，需使用 Foreground Service 保活
  • 数据备份：离线后数据仅存手机本地，需考虑导出/备份机制（现有 CSV 导出功能可复用）
  • 多设备同步：离线模式下无法多设备共享数据，需评估是否为真实需求
