3V3.1 空白页面真实根因与修复

3.1 故障现象

V3.0/V3.0.1 APK 安装到魅族20（Android 16，API 36）后，启动页面一直空白。

真实根因（经 buildozer 源码验证）

V3.0.1 的“6 根因”多为正确工程加固但非决定性。致命根因：buildozer.spec 中的 python_depends 键根本不存在于 buildozer 源码，被静默忽略，导致 flask-sqlalchemy/flask-wtf/flask-login 从未打进 APK → from app import app 即 ModuleNotFoundError → Flask 永远起不来 → WebView 连接拒绝 → 白屏；报错仅输出到 logcat，用户完全无感知。

3.2 根因链路

#根因验证依据
①决定性python_depends 不是有效 buildozer 键，Flask 扩展库全部缺失buildozer targets/android.py 无此键；check_configuration_tokens() 只校验 5 项，未知键静默忽略
②Android 9+ 明文 HTTP 默认禁，WebView 可能拒载 http://127.0.0.1targetSdk≥28 时 usesCleartextTraffic 默认 false
③启动时序依赖固定延迟，首次建表可能 >10 秒低端机首启建 22 张表耗时不可预测

3.3 V3.1 修复方案

#修复文件
1requirements 直接列出全部包（p4a 对无 recipe 的纯 Python 包自动 pip 安装），删除无效 python_dependsbuildozer.spec
2android.extra_manifest_application_arguments 注入 usesCleartextTraffic="true"buildozer.spec + extra_manifest_args.txt
3WebView 首屏加载内嵌诊断页，JS 每 700ms 轮询 /login，就绪后自动跳转（同源免 CORS）main.py
4启动失败 12 秒后将 traceback 渲染到 WebView，不再白屏盲调main.py
5双通道日志（logcat + files/app_debug.log）+ setWebContentsDebuggingEnabled 远程调试main.py
6requirements 追加 greenlet（有 recipe） ⚠️ V3.1.1 已移除（见 3.5.2）buildozer.spec

requirements 最终形态（V3.1.1 当前）

requirements = python3,hostpython3,openssl,sqlite3,pyjnius,kivy,flask,sqlalchemy,
  markupsafe,flask_sqlalchemy,flask_wtf,flask_login,werkzeug,requests,
  itsdangerous,click,blinker,jinja2,wtforms
V3.1.1 变更：移除 greenlet（V3.1 曾短暂加入；它是 V3.0 成功构建集之外唯一新增的需 C 交叉编译的 recipe，成为 V3.1 构建失败的高危因素。SQLAlchemy 同步模式缺失时自动纯 Python 回退，零功能损失）。

3.5 V3.1.1 补丁：AI 图片识别直连修复 + 构建收窄（2026-10-08）

3.5.1 问题一：网关配置了支持图片的模型，却提示「所有 AI 配置均无法识别图片」

旧逻辑缺陷（ai_service.py）

按模型名关键词白名单（gpt-4o/vision/vl/4v/claude-3）判断“是否支持图片”：用户经自建网关（NewApi/OneAPI）配置的自定义模型名（实际支持图片）不含关键词 → 被硬改为 gpt-4o-mini → 网关无此模型名 → 请求必败 → 误报「所有 AI 配置均无法识别图片」，误导用户。

#V3.1.1 修复（37 项单测全绿）说明
1用户原始模型名优先直连客户端不做能力猜测，模型是否支持图片由 AI 服务端判定
2常见 vision 模型兑底仅原始模型失败后依次尝试 gpt-4o-mini / gpt-4o / gemini-2.0-flash（不与原始重复）
3真实错误透出收集每次失败真实报错，全部失败时透出最后 3 条（含配置名/模型名/错误详情），非 JSON 响应返回 422
4MIME 嗅探修复base64 解码头从 8 字节扩至 18 字节，修复 WEBP 魔数 RIFF....WEBP 的 [8:12] 切片被截断
5null 字段清洗r.get(x, default) 在值为 null 时返回 None → str(None)='None'；改用 r.get(x) or default
6base64 换行清理 + max_tokens 4000剥离客户端插入的 CRLF；长列表识别不再截断

3.5.2 问题二：V3.1 触发的 Actions 构建失败（run 37746146665）

#修复（buildozer.spec + build.yml）说明
1移除 greenletV3.1 新增的唯一需 C 交叉编译的 recipe（高危失败源）；SQLAlchemy 同步模式自动纯 Python 回退

3.6 V3.2.0 架构级重构：webview bootstrap，彻底移除 Kivy/SDL/GL（2026-10-09）

3.6.1 决定性线索

所有版本（含 V1.x）从未在真机上显示过内容

用户反馈 V1.x 同样无法打开、全部空白、等待超 1 分钟。V3.1 内嵌诊断页（不依赖 Flask 也能显示）都出不来，说明故障在「Kivy App → GL 初始化 → Clock → pyjnius WebView」这条链的早期——所有版本共用的最大组件即 Kivy + SDL/GL 渲染链，从未被任何一次真机运行验证过。

3.6.2 新架构：p4a 官方 webview bootstrap（源码级验证）

维度（V1.x~V3.1.1，sdl2 bootstrap）新（V3.2.0，webview bootstrap）
WebView 由 Python(Kivy App/Clock/pyjnius) 创建纯 Java 层（PythonActivity 直接 new WebView + setContentView）
依赖 Kivy/SDL/GL 渲染链完全移除，requirements 已剔除 kivy
启动展现依赖 Python 活着Java 启动图 + assets/_load.html Loading 页，Python 未活也可见
库加载失败白屏无提示Java AlertDialog 直接报错
Python 侧 JS 轮询跳转Java WebViewLoader 轮询 127.0.0.1:5000 自动 loadUrl（--port 默认 5000）
需手工注入 cleartextmanifest 模板自带 usesCleartextTraffic=true
仅 logcat/内置日志三通道日志（logcat + 内置 + 外置 USB 可读）+ 启动 marker + 重试3次 + Toast
构建产物黑盒CI 解包自检：12 核心 py + 20+ 模板 + Flask 12 依赖逐项验证

3.6.3 启动链路（新架构）

Java: onCreate → 解包 private.tar/libpybundle → 加载库(失败弹 AlertDialog)
      → WebView 创建 + _load.html(Loading 页，立即可见)
      → PythonThread 启动 main.py / WvThread 轮询 5000
Python: 环境设置(GIFT_DATA_DIR) → marker(dirs_ready)
        → 后台线程 Flask → marker(app_imported → flask_running)
        → 端口 5000 监听 → Java loadUrl("http://127.0.0.1:5000/")
失败分支: Flask 3 次重试全败 → last_error.txt(外置) + Toast，进程保活取证

3.6.4 验证结果与真机取证指引

  • 启动链路模拟测试 15/15 全绿：端口 5000、marker 五阶段、日志三通道、/login 200（v3.2.0）、静态资源、watch 成功
  • 真机预期：启动图 → Loading 页 → 自动跳登录页；若 Loading 停留不动，USB 连接电脑在 Android/data/<包名>/files/ 提取三文件即可定位：app_debug.log（全程日志）、startup_marker.txt（Python 是否运行过）、last_error.txt（失败 traceback）
